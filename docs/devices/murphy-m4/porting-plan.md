# Murphy M4 — план портирования и матрица гипотез

Рабочий документ для экспериментов на живом устройстве. Справочная часть (железо, прошивки,
источники) — в [README.md](README.md) и [sources.md](sources.md).

Принцип: **сначала измерить, потом собирать.** Почти всё, что ниже, определяется за первый
час работы с устройством — и после этого «порт» превращается в заполнение одной структуры
`BoardProfile`.

---

## 1. Что известно и с какой уверенностью

| Утверждение | Уверенность | Откуда |
|---|---|---|
| MCU — ESP32-S3 | **высокая** | OTA-манифест MurphyOS `"chip_family": "ESP32-S3"`, заголовок образа v1.2.16 |
| Панель 800×480 | **высокая** | владелец пишет «как у X4»; сходится арифметически: √(800²+480²)/4.26" = 219 ppi ≈ заявленные ~220 |
| Стекло — Good Display GDEQ0426T82 | **высокая** | это и есть 4.26" 800×480 панель из X4; другой такой в обиходе нет |
| Контроллер — SSD1677 либо UC8179/UC8279 | **средняя** | все три встречаются на этой панели в разных партиях X4/X4 Pro |
| Тач есть, модель неизвестна | высокая / — | отзывы владельцев |
| Фронтлайт двухканальный (warm+cold) | **средняя-высокая** | пользователи регулируют цветовую температуру → почти наверняка два PWM-канала |
| SD — SDMMC | средняя | у M3 и X4 Pro так; у M4 карта съёмная и есть USB-OTG |
| PSRAM есть | средняя | у M3 8 МиБ; типично для S3-модулей этого класса |
| Флеш 16 МиБ, без шифрования и secure boot | средняя | подтверждено на M3, ожидаемо на M4 |

Всё «среднее» проверяется за один вечер (раздел 4).

## 2. Матрица комбинаций

Оси неопределённости и то, что каждая означает для работы.

### A. Контроллер панели — главная развилка

| Вариант | Драйвер в SDK | Что делать |
|---|---|---|
| **SSD1677** | `Ssd1677Driver` | ничего не писать: конфиг X4/GDEQ0426T82 — дефолтный |
| **UC8179** | `Uc8179Driver` | взять как есть; в X4 Pro эти два различаются автодетектом при загрузке |
| **UC8279 (800×480)** | `Uc8279X4Driver` | взять как есть; **не путать** с `Uc8279Driver` для X3 (792×528) |
| **UC8253** | `Uc8253MurphyDriver` / `Uc8253X3Driver` | практически исключено: контроллер не адресует 800×480 |
| что-то иное | — | худший сценарий: писать драйвер, вынимать LUT-и из дампа |

Первые три = работа уже сделана. Вероятность попасть в них высокая.

### B. Тач

| Вариант | Поддержка | Прецедент |
|---|---|---|
| **GT911** | есть в SDK | X4 Pro, Sticky, LilyGo |
| **CHSC6x** | есть в SDK | Murphy M3 |
| **FT6336U** | нет драйвера | Good Display указывает его для 3.7" панелей с тачем |
| иное | нет | писать драйвер поверх I²C |

Определяется I²C-сканом: `0x5D`/`0x14` → GT911, `0x2e` → CHSC6x, `0x38` → FT6x36 (но `0x38`
у M3 занят датчиком AHT30 — различать по ответу, а не по адресу).

### C. Фронтлайт

| Вариант | Поддержка |
|---|---|
| Двухканальный warm/cold PWM | есть: `FrontlightConfig` + `FrontlightManager` (как X4 Pro: GPIO8 ch4 / GPIO9 ch5, 10 кГц, 10 бит) |
| Одноканальный PWM | есть (de-link, M3, LilyGo) |

### D. SD

| Вариант | Поддержка |
|---|---|
| 4-битный SDMMC | есть: `FREEINK_SD_SDMMC=1` + `USE_BLOCK_DEVICE_INTERFACE=1` (de-link, M3) |
| 1-битный SDMMC | есть (X4 Pro) |
| SPI | есть (X4, Sticky) |

Отдельно: у X4 Pro линия питания карты `GPIO5` **active-LOW** и её надо импульсно дёрнуть
перед монтированием — у M3 та же история с `GPIO10`. Если карта «не видна» — искать этот пин,
а не чинить драйвер.

### E. Кнопки

| Вариант | `InputStyle` | Прецедент |
|---|---|---|
| Цифровые active-low GPIO | `DigitalButtons` | X4 Pro, M3 |
| ADC-лесенка | `XteinkAdcLadder` | X4, de-link |

### F. Прочая периферия (не блокирует чтение)

RTC (`RX8010` @0x32 у M3, `BM8563`/`PCF8563` у X4 Pro/Sticky), датчик температуры/влажности
(`AHT30` @0x38 у M3, `SHT40` у Sticky), гейдж батареи (`CW2017` @0x63 у X4 Pro, `BQ27220` @0x55)
или простой ADC с делителем (у M3 — `GPIO9`, множитель 2.0).

## 3. Профили-кандидаты в SDK

Пять готовых профилей, от которых можно отталкиваться. Сравнение по близости к ожидаемому M4:

| Профиль | MCU | Панель | Тач | Фронтлайт | SD | Кнопки | Близость к M4 |
|---|---|---|---|---|---|---|---|
| **`XTEINK_X4_PRO`** | S3 | 800×480, SSD1677 **или** UC8179 (автодетект) | GT911 | **warm+cold** | 1-бит SDMMC | цифровые | **лучший шаблон** |
| `DE_LINK` | S3 | 800×480, SSD1677 | нет | одноканальный | 4-бит SDMMC | ADC-лесенка | очень близко, но без тача |
| `STICKY` | S3 | 3.97" 800×480, SSD1677 | GT911 | — | SPI | — | тот же драйвер панели |
| `XTEINK_X4` | C3 | 800×480, SSD1677 | нет | нет | SPI | ADC-лесенка | эталон панели, но другой MCU |
| `MURPHY_M3` | S3 | 240×416, UC8253 | CHSC6x | одноканальный | 4-бит SDMMC | цифровые | родственник по бренду, **чужая панель** |

Ключевой вывод: **`XTEINK_X4_PRO` — точка старта.** Совпадает по всему списку фич M4
(S3, 800×480, тач, тёплый/холодный свет, SDMMC, автодетект контроллера); отличаться будут пины.

Профиль X4 Pro в `BoardConfig.h:1082` вдобавок хорошо прокомментирован — там прямо отмечено,
что подтверждено на железе, а что было ошибкой ранних предположений (порядок SCLK/MOSI,
перепутанные INT/RST у GT911). Полезно как образец того, что именно надо проверить у M4.

## 4. Дерево экспериментов

### Шаг 0 — до включения

- [ ] Запросить у продавца **код активации по UID** (Settings → последний пункт → Activate Device)
- [ ] Запросить схемы M4 у corogoo / продавца (см. README 2.5)
- [ ] `pip3 install esptool`
- [ ] Записать версию стоковой прошивки и её род (MoFei `EPD426` vs MurphyOS)

### Шаг 1 — дамп (обязательно первым)

```bash
esptool.py --port /dev/cu.usbmodem* flash_id            # чип, размер флеша
esptool.py --port /dev/cu.usbmodem* read_flash 0 ALL murphy_m4_dump.bin
```

Проверить: `esptool.py get_security_info` — нет ли flash encryption / secure boot.
**Хранить дамп приватно** (в NVS пароли WiFi); перед публикацией вычистить `0x9000`–`0xE000`.

Критерий: файл на 16 МиБ (или сколько покажет `flash_id`), не состоящий из `0xFF`.

### Шаг 2 — определить контроллер панели, не трогая устройство

Работа по файлу, 10–20 минут:

```bash
strings -n 6 murphy_m4_dump.bin | grep -iE "ssd1677|uc8179|uc8279|uc8253|gdeq|gdey"
strings -n 6 murphy_m4_dump.bin | grep -iE "gt911|chsc|ft6[0-9]{3}|0x5d|touch"
```

Плюс поиск сигнатур: размер фреймбуфера (48000 = 800×480/8 против 12480 у M3), команда `0x61`
(TRES) с параметрами гейтов, init-последовательности. Ориентир — тот же метод, которым для M3
вытащили OEM-волновые формы.

Исходы:

| Что нашли | Куда дальше |
|---|---|
| SSD1677 / UC8179 / UC8279 | шаг 3 с соответствующим драйвером — самый вероятный и лёгкий путь |
| ничего узнаваемого | сравнить с `m4/murphy-26-0526-1.2.16.bin` из репозитория Murphy (это форк CrossPoint — там имена функций CrossPoint) |
| явно другой контроллер | худший сценарий: вынимать init + LUT из дампа, писать драйвер |

### Шаг 3 — I²C-скан и GPIO-пробы

Собрать пробу-скетч (образцы: `m3/probes/*.cpp` в репозитории Murphy) и залить.
**Только после шага 1.**

Ловушка, стоившая времени на M3: шина может быть за гейтом питания. Если скан пуст — перебрать
кандидатов на гейт, подняв каждый GPIO по очереди, прежде чем делать вывод «тача нет».

Ожидаемые адреса: `0x5D`/`0x14` GT911, `0x2e` CHSC6x, `0x32` RX8010, `0x38` AHT30/FT6x36,
`0x51` PCF8563/BM8563, `0x55` BQ27220, `0x63` CW2017.

### Шаг 4 — bring-up дисплея

Собрать CrossPoint с профилем-копией `XTEINK_X4_PRO`, подставив найденные пины.
Цель — любое осмысленное изображение.

| Симптом | Наиболее вероятная причина |
|---|---|
| экран не меняется | не тот CS/DC/RST, либо панель не запитана (искать powerEnable) |
| мигает, но не фиксирует | несовпадение init и банка LUT — на M3 это была «пакетная сделка» |
| призраки, грязный фон | LUT без kick-фазы / без DC-баланса (классическая ошибка M3) |
| зеркальное или перевёрнутое | mount-трансформ: `ROTATE_180` / mirrorX / mirrorY в профиле |
| артефакты на высокой частоте | снизить `displaySpiHz` (20 МГц → 5 МГц) |

### Шаг 5 — остальное

SD (не забыть про active-low питание карты) → кнопки → тач (оси и `swapXY`/`flip` проверяются
тапом по четырём углам, как делали на M3 и X4 Pro) → фронтлайт → батарея → сон.

### Шаг 6 — оформление

Board-профиль и драйверные правки → в `freeink-sdk` (маршрут, который прямо назвал мейнтейнер);
дамп и находки по железу → в `crosspoint-reader/Murphy`. Всё промежуточное живёт в форке,
ветка `device/murphy-m4`.

## 5. Риски и откат

| Риск | Смягчение |
|---|---|
| Кирпич при неудачной прошивке | дамп с шага 1: `esptool.py write_flash 0x0 murphy_m4_dump.bin` |
| Стоковая ОС требует код активации после отката | код запрошен у продавца заранее (шаг 0) |
| Заливка чужой прошивки (M3-сборка, образ для C3) | не ставить M3-релиз; в апстриме есть проверка `chip_id` (PR #2880), но полагаться на неё рано |
| Порча панели чужими волновыми формами | однократные попытки безопасны; не гонять неверные LUT-и часами |
| Утечка паролей WiFi из дампа | чистить NVS `0x9000`–`0xE000` перед публикацией |
| Чужие PR переписываются (mr-tbot уже пересоздавал ветку) | фиксировать конкретные коммиты, а не следовать за веткой |
